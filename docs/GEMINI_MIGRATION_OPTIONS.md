# Moving to Gemini, and offering a real-time (Gemini Live) path next to STT-LLM-TTS: research and options (2026-10-15)

Research only. Nothing was changed or tested against Gemini (no Gemini key is configured, so no call was made). Facts about Gemini come from Google's documentation pages read today (listed at the end), through a summarising fetch tool, so read them as "what the docs say", and re-check model names and limits before building. Facts about our project come from reading the code and the stored data.

## 1. How our project is coupled today (the part that decides how easy this is)
- **The language model is reached through one narrow door.** `engine/author.py: get_azure_client()` returns an Azure OpenAI client, and the whole tutor loop uses exactly one call on it: `client.chat.completions.create(model, messages, tools, tool_choice="auto", temperature=0.7, max_tokens=6000)`, then reads `choices[0].finish_reason`, `.message.content`, `.message.tool_calls[i].id / .function.name / .function.arguments`, and `usage`. Three other places use the same call shape: page summaries (`engine/summary.py`, `backend/page_summary.py`, temperature 0), and the evaluation judge (`tests/eval_judge.py`, with `response_format=json_object`). About 23 test files replace `get_azure_client` with a fake, so the seam already exists and is tested.
- **Speech out is ElevenLabs with character timestamps**, called inside the draw handler for every element (`engine/voice.py`). The browser reveals a drawing at the time of its `[[MARK:id]]` token in the audio. **Measured on the 468 stored narrations: the first marker is at a median of 0.06 s, 90th percentile 0.56 s** (maximum 62 s, rare), because the prompt puts the marker in the first sentence. So precise timestamps matter much less than the design suggests; a rough timing would do for about 9 in 10 drawings. The code already has a synthetic-timing fallback (`_generate_fallback_speech_alignment`).
- **Speech in is Deepgram** (browser microphone, relayed through a backend WebSocket, text comes back and goes into the normal chat message). Nothing in the tutor knows about audio.
- **Frozen items that bind this work:** the system prompt and tool text (digests pinned in a test), and the rule that a new model needs its own baseline (`docs/BASELINE.md` is all gpt-4.1-mini and does not carry over).

## 2. Part A: replacing Azure OpenAI with Gemini for the tutor loop (easiest first)
Gemini models listed in the docs today: `gemini-3.8-flash` (stable, new), `gemini-3.6-flash`, `gemini-3.5-flash-lite`, `gemini-4-argon` (flagship; not on the free tier). Thinking cannot be switched off on 3.8 (levels low, medium, high; default medium); `gemini-3.6-flash` and `3.5-flash-lite` offer `minimal`. Prices listed per million tokens: 3.8-flash and 3.6-flash 0.75 input and 3.75 output until 31 Dec 2026 (double afterwards); 3.5-flash-lite 0.30 and 2.50; thinking tokens are billed as output. Free tier exists for the Flash models (content may be used to improve Google's products). Our measured turn time on gpt-4.1 is 8 to 15 s for about 1,500 output tokens, so thinking latency is the number to watch.

**A1. Google's OpenAI-compatible endpoint (about 20 lines).** Use the `openai` package we already have: `OpenAI(base_url="https://generativelanguage.googleapis.com/v1beta/openai/", api_key=GEMINI_API_KEY)`, model `gemini-3.6-flash` and so on; the loop and the tests stay unchanged. Cautions: Google says OpenAI-library support "is still in beta"; its function-calling section on that page only shows a minimal example (nothing on parallel calls, tool messages or `max_tokens`); and community reports describe Gemini 3 models returning a 400 error on the second step of a tool loop when the "thought signature" of the earlier function call is not sent back (our loop appends the model's message to the history and repeats up to 20 times, so it is exactly that pattern). I could not confirm from Google's pages how the compatible endpoint hands the signature back. This is the cheapest thing to try and the first thing to test (section 5, step 0).
**A2. LiteLLM as the single door (about 40 lines plus a dependency).** One library, same OpenAI-shaped calls, `azure/gpt-4.1` or `gemini/gemini-3.6-flash` chosen by a string; its documentation says it stores and replays Gemini 3 thought signatures itself. Any provider could be added later by changing a setting. Cost: a new dependency and its version drift.
**A3. A small adapter on Google's own SDK `google-genai` (about 200 lines, most robust).** A class with the same `.chat.completions.create(...)` surface that converts our messages and tools to Gemini's format and back, keeping the signatures the SDK returns. No dependency on the beta compatibility layer; more code, tested with the same fakes.
**The seam for all three:** one new module `engine/llm.py` with `get_llm_client()` and the model names, selected by `LLM_PROVIDER=azure|gemini`, with `azure` as the default so nothing changes until the switch is thrown; `get_azure_client` stays as an alias so the 23 test files are untouched. The evaluation judge stays on the fixed Azure model (it is already configured separately) so that changing the author does not change the judge. The prompt and tool text are not touched.
**Standing rules that apply:** a new baseline on the same measurements before anything is claimed (eval topics, the GPS replay, the overlap runs), a result counts only outside the run-to-run range, and the comparison model is gpt-4.1, not the old mini baselines.

## 3. Part B: two voice paths that can both be used
**Path 1, the current pipeline (STT, LLM, TTS), stays as it is** and gets Gemini only as the language model (Part A). Optional pieces if everything should come from Google: Gemini speech generation (`gemini-3.8-flash-tts`, `3.8-flash-lite-tts`; 30 voices, streaming PCM) in place of ElevenLabs. The documentation mentions no word or character timestamps, so the reveal time would be estimated (our own data above says that is acceptable for most drawings, to be verified on a sample); and Gemini audio understanding could replace Deepgram, but Deepgram's live partial results work today and are the lowest-risk piece to keep.

**Path 2, a real-time path with the Gemini Live API (audio in, audio out), as a second mode.** What the docs say: a stateful WebSocket; audio in as 16 kHz 16-bit PCM, audio out 24 kHz PCM; function calling is supported (the client must answer each call itself; calls are synchronous by default, and the Live model `gemini-3.1-flash-live-preview` cannot do asynchronous calls); voice-activity detection with barge-in is built in; the models listed are `gemini-3.8-live` (low latency, "no reasoning delays") and `gemini-3.8-live-extended-thinking`; native-audio models answer in audio only (text only as a transcription of the spoken output, with no timing data); audio sessions are limited to 15 minutes and one connection lasts about 10 minutes unless context-window compression and session resumption are switched on; context 128k tokens. Pricing listed: audio in $0.005 per minute, audio out $0.018 per minute (text 0.75 and 4.50 per million tokens).
How it would fit our project with the least change:
1. A new backend WebSocket endpoint, for example `/api/ws/live/{notebook_id}`, relays between the browser and the Live API (server to server, like the Deepgram relay we already have; the key stays on the server, so no ephemeral tokens are needed).
2. The Live model is given our board tools as function declarations, and each call is executed by the existing handlers (draw, modify, annotate, start page, get state) with their validators, rejection messages and persistence unchanged. The one difference: the handler's speech-synthesis step is skipped, because the model is already speaking. A small change: let the draw handler take the audio from a supplied source instead of calling ElevenLabs.
3. Synchronising the drawing with the voice: the model's audio arrives in chunks and the tool call arrives in the same stream. Reveal the drawing when playback reaches the point where the tool call arrived (we know how many audio bytes came before it). The audio between two tool calls is saved as that element's audio file, with a marker time of 0, so the stored events, replay and export keep the format they have now.
4. The browser gets a mode toggle ("Classic" or "Live") and two audio pieces it does not have yet: microphone capture to 16 kHz PCM and playback of 24 kHz PCM (an AudioWorklet). This is the largest piece of work.
5. Needs the owner's decision: the frozen prompt and tool text describe a `narration` argument and `[[MARK:...]]` tokens for a model that does not speak; in Live mode the model speaks by itself, so Live needs its own system instruction and its own tool declarations. The existing path would not be touched.
**Open risks of Path 2 (all unmeasured):** whether an audio-first model writes long, valid SVG in tool arguments as reliably as a text model (the board quality and the validator's rejection rate would have to be measured on the same prompts); the preview status of some Live models and their rate limits; community reports of disconnects (1008/1011) and delayed or sparse transcriptions in sessions of 10 to 14 minutes; no per-word timing; the cost of keeping a session open.
**A cheaper variant (Path 3):** Live handles the conversation and calls one tool `ask_tutor(request)` that runs the existing tutor loop (with Gemini through Part A) and returns the narration to speak. It reuses everything, but each drawing costs the 10 to 15 s model turn while the voice waits (asynchronous tool calls exist on `gemini-2.5-flash` Live but not on 3.1 Flash Live), so it would feel less real-time than Path 2. Mentioned for completeness; not recommended as the first step.

## 4. Choosing the path at run time ("either path")
- `LLM_PROVIDER` (azure or gemini) for the language model, `VOICE_MODE` (classic or live) for the voice path, both read at start, both defaulting to today's behaviour. Classic mode keeps the REST chat endpoint and the Deepgram relay exactly as they are; Live mode adds its own endpoint. Both write the same stored events, so notebooks made in either mode replay and export the same way.
- The shadow validator hook keeps working in both modes because it sits in the draw handler.

## 5. Suggested order, each step reversible
0. **A go/no-go test (hours):** with a Gemini key, run our real tool schema through a 10-step scripted tool loop on `gemini-3.6-flash` and `gemini-3.8-flash` through the compatible endpoint (A1). If it works, A1 is enough; if a 400 appears on step two, use A2 or A3.
1. **The seam (small):** `engine/llm.py` and the `LLM_PROVIDER` switch with the default unchanged; the full test suite must stay green.
2. **Gemini as the tutor (medium):** the chosen option from A1 to A3, a new baseline on the standing measurements against gpt-4.1, thinking level chosen for latency, report in the usual form.
3. **Optional, Gemini TTS (small):** behind a setting, with estimated reveal times; compare the reveal times with ElevenLabs on a sample.
4. **Live prototype (large, separate branch of work):** points 1 to 4 of Path 2 on a single page of a notebook, measuring drawing reliability, time to first drawing, interruption handling and a 15-minute session with resumption; the prompt and tools for Live proposed to the owner first.
Not needed: replacing Deepgram, a new database, or touching the validators.

## 6. What is not known
Everything about Gemini's behaviour in our loop (tool-call reliability on long SVG, thought signatures through the compatible endpoint, thinking latency, drawing quality against gpt-4.1) is untested. The model names and prices are as listed today and may change (several are dated, for example the price doubling on 1 January 2027). Live quality for board drawing is unknown.

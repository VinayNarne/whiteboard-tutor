# Overlap round: details (plan: docs/OVERLAP_PLAN.md; model gpt-4.1 throughout)

## 1. The overlap rejection message (tool-result text, `engine/author.py`; prompt and tool text untouched)
**Old:** `'X' overlaps existing 'Y' (x:60-760, y:120-470). Redraw in free space (see occupied_regions in get_current_page_state), or, if no free space is left, tell the learner and propose a new page.`
**New, a region fits:** `... overlaps existing 'Y' (x:60-760, y:120-470). Your drawing is about 120x80 px. A free region where it fits: x:20, y:480, width:1160, height:300. Redraw it inside that region.`
**New, nothing fits:** `... Your drawing is about 500x400 px and no free region that large is left on this page: about 18% of the canvas is free, and the largest free region is x:.., y:.., width:.., height:... Draw something that fits there, or tell the learner the page is full.`
**Region (`find_free_region`, `engine/validator.py`, code only):** the same element boxes the overlap check uses; shapes thinner than 20 px ignored; 10 px gap around every element; 10 px grid inside a 20 px canvas margin; the free rectangles at least as large as the drawing; **the largest wins, the one nearest where the model tried to draw on a tie.**
*Deviation from the rule shown before editing:* I first chose "nearest" and the first sample returned a strip exactly as tall as the drawing (80 px), which leaves no margin for the model's coordinates; I changed it to "largest" and said so. Nothing is moved for the tutor.
**The old text itself told the tutor to "propose a new page"** and the frozen prompt says "PROPOSE a new page in your chat reply and wait". That is where the permission asking comes from.

## 2. Repeat cap
Key: (new element, element it overlaps), per turn. 1st and 2nd rejection: the full message. From the 3rd: only `Free region for 'X' (about WxH px): x:.., y:.., width:.., height:..` (or `No free region for 'X' ...` with the room left); the drawing is still rejected; `overlap_cap_reached` (element, existing element, count, cap 2) is logged.
Tests `tests/test_overlap_message.py` (10, SQLite and Postgres): a region that fits is inside the margin, clear of every element and large enough (150 random layouts); when the code says nothing fits, brute force on the same grid finds no placement (80 random layouts); an empty page and a thin connector are free; the message names both elements, size and a region where the drawing is then accepted by the real overlap check;
the no-fit wording; the hint-only form; two full messages then hints and the log events with counts 3 and 4; another element has its own count, a new turn starts again, a drawing in free space is accepted. Full in-process suite after the change: 681 passed, 32 skipped (live-server tests).

**By the rule (counts only if all after-runs are outside the before-range): no clear change in any measure except GPS-replay overlap rejections, which are HIGHER after (3/4/6 against 2/2/2; the before range was a single value, so any variation is outside it).** Permission asks: no clear change.
**Post hoc (not agreed beforehand; read it as a lead, not a result):** the count of rejections cannot show the effect of a message the tutor only reads after its first rejection. Looking at what happened next: elements with an overlap rejection that were later drawn successfully under the same id. So in the GPS replay the tutor retried the element in free space far more often than it gave up, which also explains the higher rejection count (a retry can be rejected again). Permission asks did not fall.
**Caveats:** one model, one day, three runs of a calm replay; the real session's behaviour (7 pages, 3 asks) was not reproduced by the replay.

## 5. Scroll jump: verified in a browser (Claude's browser pane, the GPS notebook; the chat request was stubbed so no model call was made)
- **Trigger:** `frontend/src/components/ChatPanel.tsx:141`, `bottomRef.current?.scrollIntoView(...)`, in the effect that runs on every change of `chatHistory` or `isAgentThinking` (sending a message changes both: the call ran twice per send, `behavior: smooth`).
- **Why the whole page moves:** the screen-reader labels `<span className="sr-only">You: </span>` (`ChatPanel.tsx:349`, CSS `.sr-only { position:absolute }` in `index.css:94`) sit inside the chat log, whose ancestors are all `position: static`, so the labels are positioned against the PAGE and are not clipped by the log's own scrolling. 45 labels in a long chat make the document 6,057 px tall in a 720 px window although the app is `height: 100vh`, so the window itself is scrollable.
  `scrollIntoView` then scrolls the log AND the window.
- **Measured:** one send moved the window 0 -> 513 px (canvas top 19 -> -494) and the log to the bottom. **Counterfactual in the page only:** with the log made `position: relative` the document height is 720, the same two calls scroll only the log (5,705) and the window stays at 0 (canvas top 19). The page grows with chat length, so it gets worse as a session goes on (your screenshot).
- Not fixed (as agreed). Smallest candidate fixes, for the owner: give the chat log `position: relative` (one style), or scroll the log by `scrollTop` instead of `scrollIntoView`.

## 6. Speech rate (not changed)
- Set: `engine/voice.py:138`, the ElevenLabs request body is only `{"text", "model_id": "eleven_turbo_v2_5"}`: no `voice_settings`, so the provider default speed 1.0 applies. The browser has a speed menu with 1.0x, 1.25x and 1.5x only (`ChatPanel.tsx`, remembered in `voiceSpeed`): **no option slower than 1.0**.
- **Provider range, tested on the live endpoint** (docs found were secondhand and contradicted each other): `voice_settings.speed` 1.0, 0.85 and 0.7 accepted; 0.5 rejected with `invalid_voice_settings` ("expected to be greater or equal to 0.7"). **0.85 works with no prompt change.**
- **Drawing sync:** the same call returns the character timings, and they stretch with the audio (one sentence: 5.80 s at 1.0 became 6.73 s at 0.85, 8.03 s at 0.7). The reveal times come from those timings, so the sync stays consistent. Cost: speech takes about 17% longer and drawings appear later; at 0.85 the measured 171 to 178 words per minute become about 145 to 150.
- Not tested: a whole session at 0.85, and the browser speed menu on top of it (1.25x would give 1.06).
